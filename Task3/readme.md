## Описание взаимодействия

Сервис core-app осуществляет запрос к `ins-product-aggregator` раз в 15 минут, а `ins-comp-settlement` — раз в сутки (ночью), при формировании реестра оформленных страховок. Иногда команда сталкивается с ошибками взаимодействия между этими сервисами. Они связаны с задержками ответов или ошибками при взаимодействии с API страховых компаний.
Дополнительно сервис `ins-comp-settlement` раз в сутки осуществляет запрос в core-app по REST API для получения всех оформленных за день страховок. Эти данные он использует.
В ближайшее время InsureTech планирует подписать агентское соглашение ещё с пятью страховыми компаниями

## Проблемы и риски, связанные с 
- Увеличение страховых компаний увеличивает общее время выполнения запроса
- Возникновение ошибки или высокой задержки в синхронном запросе влияет на весь запрос, в результате частые ошибки, таймауты, медленная работа
- Периодические запросы с нескольких сервисов через `ins-product-aggregator` могут привести к одновременному выполнению запросов к API страховых компаний, что может привести к нарушению SLA и/или сбоям выполнения запроса
- Редкое выполнение из `ins-comp-settlement` (раз в сутки), сбой выполнения запроса может привести к устареванию данных
- Единая точка отказа в интеграциях со страховыми. Если произойдет сбой, то будут недоступны все страховые компании
- Сложности масштабирования и развития общего `ins-product-aggregator` Внесение изменений и обновление в рамках интеграции с одной компанией ведет за собой риски сбоев со всеми компаниями. Требуется полное перетестирование со всеми компаниями, даже если изменения не добавлялись
- Отсутствует стратегия повторных запросов если запрос к страховой компании не выполнен
- По API для партнеров отсутствует RateLimit, один клиент может злоупотреблять запросами и забрать всю нагрузку на себя, в результате нарушается SLA для других клиентов
- Приложение падает, команда узнает об инцидентах от пользователей, отсутствует мониторинг


## Решение
- Перейти на Event-Driven архитектуру. Использовать Kafka для обмена между сервисами
- `ins-product-aggregator` периодически должен опрашивать страховые компании для получения информации о продуктах. Кэшировать ответ, при наличии изменений отправлять данные в топик `ins-products-topic`. Сервисы `ins-comp-settlement` и `core-app` потребители
- сервисы `ins-comp-settlement` и `core-app` могут принудительно запросить всю актуальную информацию о продуктах (например при инициализации или восстановлении после сбоя) 
- При оформлении страховки клиентом `core-app` должен формировать сообщение о продаже в топик `ins-sale-topic`, обязательно использовать паттерн **transactional outbox**. Потребитель `ins-comp-settlement`
- Если в `ins-product-aggregator` потребуется реализовывать сильно отличающиеся от других сложные методы интеграции, то интеграцию с этой компанией рекомендуется выделять в отдельный сервис
- В API партнеров реализовать паттерн RateLimit для ограничения запросов клиентов
- Реализовать мониторинг сервисов с информированием о сбое
